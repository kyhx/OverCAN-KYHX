## 一、总体判断

| 维度 | 判定 | 依据 |
| --- | --- | --- |
| 技术路线可行性 | ✅ 高 | 器件与芯片资源匹配，无原理性错误 |
| 硬件成本可行性 | ✅ 高 | 全系统约 ¥310~560（不含打样与仪器） |
| 电气正确性 | ⚠️ 中 | 5 个 P0 阻塞项已识别（见设计规格 §11.2） |
| 指标可信度 | ❌ 低 | **全部指标为分析级，无一项经实测** |
| 执行风险 | ⚠️ 中偏高 | 零代码、零实测、零仓库；范围（3 板 + 6 场景）大于深度 |
| 求职价值 | ✅ 高 | 主方向（分布式 CAN 控制节点）选得准，**但价值取决于深度而非广度** |

**核心结论**：方案可动手，但当前瓶颈不是"想得不够多"，而是**没有一行代码和一个实测数字**。本文给出的是"怎么把方案做成、并做出可验证的深度"。

## 三、协议与架构方案

### 3.1 从自研协议迁移到 CANopen（推荐）

设计规格 §5 给出的自研编码已自洽可用。若面向车载/工业岗位深化，建议迁移到 **CANopen（CiA-301）**——它顺手把优先级排序也变成标准做法（ID 越小优先级越高，EMCY 最高、Heartbeat 最低）：

| COB-ID | 功能 | 对应设计规格中的角色 |
| --- | --- | --- |
| 0x000 | NMT 网络管理 | 广播命令 0x100 |
| 0x080 | SYNC 同步 | 新增 |
| 0x081 / 0x082 | EMCY 紧急事件 | 事件帧 0x011 / 0x021 |
| 0x181 / 0x182 | TPDO1 周期遥测 | 遥测 0x210 / 0x220 |
| 0x201 / 0x202 | RPDO1 命令 | 命令 0x110 / 0x120 |
| 0x581/0x582、0x601/0x602 | SDO 上下载（参数、标定、升级） | 新增能力 |
| 0x701 / 0x702 | Heartbeat 心跳 | 心跳 0x300 |

**不必从零实现**：使用 **[CANopenNode](https://canopennode.github.io/CANopenNode/index.html)**（工业界事实标准开源栈，ANSI-C），官方已有 **[CanOpenSTM32](https://relatedrepos.com/gh/CANopenNode/CanOpenSTM32)** 移植。把精力留给固件升级、网关与故障处理这些**你自己的东西**。

### 3.2 协议库与 DBC

| 做法 | 收益 |
| --- | --- |
| **发布 `can_distributed.dbc`** | 帧格式由机器校验，消除手写位域 bug；DBC 是车载行业事实标准交付物 |
| **cantools 生成编解码代码** | 帧定义与代码永不脱节；CI 中做一致性检查 |
| 协议库**零 HAL 依赖**（纯 C） | 可在 PC 上单元测试 + 被两块不同 MCU 共用（"异构系统"在代码层的体现） |
| 禁用 **C 位域**解析报文 | 位域布局为实现定义，跨编译器不可靠；用手写移位与掩码 |
| 协议内统一**小端**并写入规范 | 避免跨平台解析歧义 |
| 错误码统一枚举 | 错误可上报、可统计、可测试 |
| 协议库不使用 `malloc` | 嵌入式可预测性，便于 PC 测试对比 |

### 3.3 代码骨架

**分层原则**：`应用层 → 中间件（CANopen/分段/日志/参数） → 协议库（纯 C） → 驱动层 → HAL/BSP`。
最关键的一条：**协议库必须不依赖任何 HAL**。

```
can-distributed-node/
├── docs/                      # 本文档体系 + protocol.md + adr/ + can/*.dbc
├── firmware/
│   ├── common/                # ★ 跨平台共享
│   │   ├── protocol/          # 纯 C：can_frame / isotp / heartbeat / crc
│   │   └── utils/
│   ├── master-esp32s3/        # ESP-IDF 工程 + partitions.csv + sdkconfig.defaults
│   ├── node-stm32/            # 节点共用工程（宏区分节点一/二）
│   │   ├── bootloader/        # IAP Bootloader + bootloader.ld
│   │   └── app/               # app.ld（FLASH ORIGIN 指向 App 区）
│   └── hal/
├── tests/                     # PC 侧单元测试 + fuzz/
├── tools/                     # can_monitor.py / hil_test.py / ota_client.py
├── hardware/                  # 原理图 / PCB / 引脚表
└── .github/workflows/         # CI：多目标构建 + 协议测试
```

| 约定 | 建议 |
| --- | --- |
| 字节序 | 协议内统一小端 |
| 位域 | 禁用 C 位域，手写移位/掩码 |
| 错误码 | 统一枚举（`PROTO_OK` / `PROTO_ERR_CRC` / `PROTO_ERR_TIMEOUT` / `PROTO_ERR_STATE`） |
| 内存 | 协议库不使用 `malloc` |
| 不变量 | 关键状态转换加断言，Release 下编为安全兜底 |
| 版本 | 协议版本与固件版本分离 |

### 3.4 技术选型对比（面试必问）

**CAN vs RS-485+Modbus vs 无线**

| 维度 | CAN (ISO 11898) | RS-485 + Modbus | 无线（ESP-NOW / LoRa） |
| --- | --- | --- | --- |
| 拓扑 | 多主总线 | 单主轮询（本质主从） | 星型 / 网状 |
| 介质访问 | **CSMA/CR + 逐位非破坏性仲裁** | 主站轮询，从站不得主动发言 | CSMA/CA / 无 |
| 实时性 | **事件驱动 + 优先级可保证**，可做最坏响应时间分析 | 由轮询周期决定，事件延迟不可控 | 不确定性大，冲突与重传导致抖动 |
| 错误检测 | CRC-15 + 位填充 + 5 种错误 + **自动重传 + 错误界定（主动/被动/总线关闭）** | CRC-16，无自动重传 | 无线层重传 |
| 速率 / 距离 | 1 Mbps@40 m，50 kbps@1 km | 最高 10 Mbps，1200 m@低速 | LoRa 数公里@极低速 |
| 多主与冲突 | **天然支持，且冲突不丢帧** | 不支持 | 冲突即丢包 |
| 成本 | 收发器约 ¥3~10/节点 | 收发器约 ¥1~3/节点 | 模块 ¥10~50/节点 |
| 领域 | 车载、工业、医疗、电梯 | 工业、楼宇自控、电表 | 消费 IoT、远程抄表 |

> **答案骨架**：选 CAN 是因为它**原生多主 + 硬件仲裁 + 硬件级错误管理与自动重传**，使"事件驱动的实时通信"成为可能，且**冲突不丢帧**；RS-485 便宜但协议层是主从轮询，无法表达优先级、事件延迟不可控；无线省布线但确定性与抗干扰无法和差分有线相比，且本项目舵机/电机是强干扰源。

**Classic CAN vs CAN-FD vs LIN vs FlexRay（车载语境）**

| | Classic CAN | CAN-FD | LIN | FlexRay |
| --- | --- | --- | --- | --- |
| 速率 | ≤1 Mbps | 仲裁段同 CAN，数据段 5~8 Mbps | ≤20 kbps | 10 Mbps |
| 数据场 | 8 字节 | **最多 64 字节** | 8 字节 | 254 字节 |
| 校验 | CRC-15 | CRC-17/21 + 增强 | 校验和 | CRC |
| 拓扑 | 总线 | 总线 | 单线主从 | 双通道，支持时间触发 |
| 定位 | 车身/工业主力 | 新车型主干 | 车门/座椅/雨刷 | 线控（渐被以太网替代） |

> **对项目的意义**：ESP32-S3 的 TWAI **仅支持 Classic CAN**，因此协议必须按 8 字节数据场设计——这正好解释了为什么要做**分段传输（ISO-TP）**。若被问"为什么不用 CAN-FD 一次多带点"，答案就是"主控不支持"，可选外挂 MCP2518FD/TCAN4550 但需权衡复杂度。

**为什么不用 MCP2515 做第一路 CAN**：ESP32-S3 内置 1 个 TWAI 控制器，无需外挂。MCP2515 只在需要**第二路 CAN**（做网关）时才用，走 SPI。

### 3.5 bxCAN 硬件验收滤波（零成本的安全与减负）

F103 的 bxCAN 有 **14 组硬件验收滤波器**（每组可配 32 位掩码模式或 16 位 ID 列表模式）。节点上电即配置为只接收：本节点命令帧（0x110 / 0x120 之一）+ 广播命令（0x100）+ 主站心跳（0x300），其余 ID 在**控制器层面直接丢弃、不进中断**——这正是 §五 安全建模中"ID 白名单"的**硬件落地机制**，同时把无效帧带来的 CPU 中断负载降为零。ESP32 侧 TWAI 用 acceptance filter（单/双滤波模式）做同样配置。

> 注意：Bootloader 与 App 的滤波配置可能不同（Bootloader 还需收 ISO-TP 升级流），跳转与进入升级模式时都要重新配置滤波器。

## 四、OTA 固件升级方案

### 4.1 为什么 OTA 是本项目最值钱的功能

因为它强制打通**存储器驱动、链接脚本、启动流程、通信协议设计、掉电安全、版本管理、安全校验**——这些都不是单点技能，而是系统级能力。且它天然产出可量化指标（升级耗时、成功率、掉电恢复率）。

本项目的"1 主 + 2 从 + 异构 MCU"结构恰好能演示**四条不同的升级链路**：

```
                  ┌────────────────────────────────────┐
   云端/上位机 ───►│ ① 核心机自升级 (HTTPS/MQTT)         │
                  │    ESP32-S3 A/B 双分区 + 回滚 + 签名 │
                  └────────────────┬───────────────────┘
                                   │
                       ② 固件仓库 (W25Q64 staging)
                                   │
                  ┌────────────────▼───────────────────┐
                  │ ③ CAN 分段传输 (ISO-TP)             │
                  │    ISR 驻 RAM / 流式写 flash         │
                  └──────┬──────────────────────┬──────┘
                         │                      │
                 ┌───────▼──────┐       ┌───────▼──────┐
                 │ 节点一 STM32  │       │ 节点二 STM32  │
                 │ ④ IAP Boot    │       │ ④ IAP Boot    │
                 │ A/B + 回滚    │       │ A/B + 回滚    │
                 └──────────────┘       └──────────────┘
```

### 4.2 链路①：核心机自升级（ESP32-S3 OTA）

**为什么不能原地升级**：ESP32 代码是 XIP（execute in place），CPU 直接从 flash 取指运行；运行时擦写自己所在分区等于自毁。**必须写非活动分区，再切换启动目标。**

16 MB flash 分区表建议：

| Name | Type | SubType | Offset | Size | 用途 |
| --- | --- | --- | --- | --- | --- |
| nvs | data | nvs | 0x9000 | 0x6000 | 24 KB 配置 |
| otadata | data | ota | 0xF000 | 0x2000 | 8 KB 启动选择 |
| phy_init | data | phy | 0x11000 | 0x1000 | 4 KB |
| ota_0 | app | ota_0 | 0x20000 | 4 MB | 应用槽 A |
| ota_1 | app | ota_1 | 0x420000 | 4 MB | 应用槽 B |
| storage | data | littlefs | 0x820000 | ~7.5 MB | **仅日志**（节点固件仓库在 W25Q64，见 §4.7；核心机自身 OTA 直接写 ota_1，无需仓库） |

**流式写入（常见误区）**：`esp_ota_begin/write/end` 是**流式**的，不需要把整个镜像收进 RAM/PSRAM——只需一个小缓冲区边收边写。

**回滚**：
```c
// 关键自检全部通过后再确认（不能放在 main() 开头）
esp_ota_mark_app_valid_cancel_rollback();
```
配合 `CONFIG_BOOTLOADER_APP_ROLLBACK_ENABLE`：若新固件启动后未在超时内确认有效就崩溃/复位，bootloader 自动回滚。**确认点必须放在"固件确实能工作"之后**，否则"能启动但跑不起来"的场景无法回滚。

**完整性与安全层次**：

| 层次 | 机制 |
| --- | --- |
| 传输完整性 | HTTPS/TLS；分块 CRC |
| 镜像完整性 | ESP-IDF 自带 SHA-256；`esp_app_desc_t` 提供版本与编译信息 |
| 镜像真实性 | **Secure Boot v2**（RSA-3072 / ECDSA 签名，公钥烧 eFuse） |
| 机密性 | **Flash 加密**（XTS-AES） |
| 抗降级 | eFuse 安全版本号，拒绝刷入低版本 |

> **面试点**：Secure Boot、Flash 加密、签名 OTA **不是一回事**。前者保证"只运行我签名的代码"，中者保证"别人读不出我的固件"，后者保证"推来的镜像可信"。三者可独立启用。

**差分升级**：可直接使用 ESP-IDF 官方组件 **[esp_delta_ota](https://components.espressif.com/components/espressif/esp_delta_ota/versions/1.1.4/examples)**，在带宽受限场景收益明显。（注意：STM32 侧 20 KB RAM 无法承载 patch 应用，差分只适合在 ESP32 上做。）

### 4.3 链路④：节点 IAP Bootloader（最硬核）

**三条硬约束决定了整个方案形态**：

| 约束 | 后果 |
| --- | --- |
| **① STM32F103C8T6 没有双 bank**（不像 F4/F7/G4 有 BFB2 硬件双区） | 必须自定义 A/B 双区，或借助外部 flash 暂存 |
| **② 只有 20 KB SRAM**，固件 64 KB | **装不下整包**，只能"边收边写 flash" |
| **③ 写/擦 flash 期间 CPU 从 flash 取指会总线 stall** | CAN 接收中断延迟飙升 → **有丢帧风险，ISR 必须搬进 RAM** |

**第 ③ 条最容易被忽略，也最能体现深度。** ST 的 Flash 编程手册明确记载：**在写或擦除 Flash 期间对 Flash 的读访问会导致总线停顿**。后果推演：

- CAN 控制器收到帧后置位中断，但 CPU 正卡在 flash 编程循环 → **中断响应被推迟到编程完成之后**
- 一次半字编程约几十微秒，一页（1 KB）擦除约 20 ms 量级
- 20 ms 内 500 kbps 线上可到达约 **8~10 帧**，而 STM32F103 的 CAN 接收**只有 3 个 FIFO 邮箱** → **会溢出丢帧**
- **对策**：CAN 接收中断服务程序与关键发送路径放入 RAM（`.ramfunc` 段 + 启动时搬运），或用"**节点请求下一块**"的拉模式替代推模式，并在擦除前暂停传输

**Flash 分区方案**：

方案 A：F103C8T6（64 KB）纯片内 A/B —— 很紧

| 区域 | 偏移 | 大小 |
| --- | --- | --- |
| Bootloader | 0x08000000 | 12 KB |
| App A | 0x08003000 | 24 KB |
| App B | 0x08009000 | 24 KB |
| 标志页 | 0x0800F000 | 4 KB |

→ 应用被压到 24 KB，**不推荐**。

方案 B（推荐）：换 **STM32F103CBT6（128 KB，引脚完全兼容）**

| 区域 | 偏移 | 大小 |
| --- | --- | --- |
| Bootloader | 0x08000000 | 16 KB |
| App A | 0x08004000 | 52 KB |
| App B | 0x08011000 | 52 KB |
| 标志/参数页 | 0x0801E000 | 8 KB |

方案 C：给节点加一片 **W25Q64（约 ¥5）** 做双区暂存，片内只留 Bootloader + 单个 App。若想保留 C8T6，这是最佳路径。

**Bootloader 技术要点**：

- **链接脚本分离**：App 的 `FLASH ORIGIN` 改到分区基址
- **向量表重定位**：App 在**最开头**（早于任何中断使能）必须 `SCB->VTOR = 0x08004000;`，否则中断仍跳向 Bootloader 的向量表
- **跳转流程（顺序不能错）**：
```c
__disable_irq();                 // 1. 关总中断
SysTick->CTRL = 0;               // 2. 关 SysTick
for (i=0;i<8;i++) NVIC->ICER[i]=0xFFFFFFFF;  // 3. 清中断使能
for (i=0;i<8;i++) NVIC->ICPR[i]=0xFFFFFFFF;  // 4. 清挂起中断（最易漏！）
HAL_RCC_DeInit(); HAL_DeInit();              // 5~6. 复位时钟与外设
__set_MSP(*(uint32_t*)APP_ADDR);             // 7. 设置 App 栈顶
((void(*)(void))(*(uint32_t*)(APP_ADDR+4)))(); // 8. 跳 Reset_Handler
```
- **踩坑**：漏掉第 4 步 → App 里偶发进错误中断，极难排查；App 里忘设 VTOR → 一开中断就跑飞，但"点灯能亮"，极具迷惑性
- **看门狗（IWDG）**：IWDG 一旦开启**软件无法关闭**。单页擦除 ~20 ms 远低于 IWDG 最短超时，无需特殊处理；但 **Bootloader 主循环与 ISO-TP 传输等待循环里必须有喂狗点**。升级期间若发生 IWDG 复位，Bootloader 应按"升级失败"处理——不写有效标志、落回旧固件
- **升级标志**：用备份寄存器 `BKP_DRx`（需开 `PWR_BackupAccessCmd`）或标志页；后者掉电更可靠且能记录版本

### 4.4 链路③：CAN 分段传输协议

CAN 单帧仅 8 字节，**必须分段**。两条路线：

| 路线 | 说明 | 评价 |
| --- | --- | --- |
| (a) 自定义分块 | 每块 128 B = 1 帧头（块号/长度/CRC16）+ 16 帧数据；节点回 ACK | 可控，但属于"再造轮子" |
| **(b) ISO-TP / ISO 15765-2** | 标准分段：SF / FF / CF / FC 四种帧 + 流控 | **推荐**，车载通用，面试认可度高 |
| **(c) CANopen SDO Block Transfer** | 工业界标准固件下载方式（已有相关专利） | 工业岗首选 |

**协议流程**：
```
1. 进入升级模式   主站发命令 → 节点置"请求升级"标志 → 软复位进 Bootloader
2. 能力握手       Bootloader 上报：芯片 ID / flash 容量 / 块大小 / 当前版本
3. 传输元数据     镜像大小 / 目标版本 / 整包 CRC32 或 SHA-256
4. 分块传输       带块号 + 块级 CRC；窗口 N 块等一次 ACK
5. 整包校验       重算并与元数据比对
6. 写有效标志     仅在校验通过后 → 切换启动区
7. 软复位跳转     启动新固件；启动自检失败则回滚
```

**关键设计决策**：
- **推模式 vs 拉模式**：推模式吞吐高但受 flash stall 影响易丢帧；**拉模式（节点就绪即请求下一块）实现简单、天然流控、绝不丢帧** —— 建议先用拉模式跑通，再优化为窗口推模式并对比吞吐
- **块级 CRC + 整包校验都要**：前者保证单块正确（错则重传该块），后者保证最终一致
- **广播升级**：同型号节点可用广播 ID 一次下发；但广播无法逐节点 ACK，需改为"升级后逐节点上报版本"确认

### 4.5 升级耗时量化（64 KB 镜像 / 500 kbps）

| 环节 | 估算 | 说明 |
| --- | --- | --- |
| CAN 传输（理想） | 64×1024×8 ÷ 500 000 ≈ **1.05 s** | 纯数据位 |
| 加 ISO-TP 开销 + ACK | ≈ **1.4 s** | 约 1.3~1.5× |
| **Flash 编程** | 32768 半字 × ~52.5 µs ≈ **1.72 s** | F103 典型 16 位编程时间 |
| **Flash 页擦除** | 64 页 × ~20 ms ≈ **1.28 s** | 中容量 1 KB/页 |
| **预期实测总计** | **4 ~ 8 s** | 取决于推/拉与是否流水 |

> 时间与页大小须以所用型号数据手册核对（F103 中容量 1 KB/页，大容量 2 KB/页）。

**最重要的结论**：

> **升级耗时由 Flash 特性决定，不由 CAN 带宽决定。** CAN 只占约 1.05 s，Flash 编程 + 擦除占约 3 s。

由此推出的优化方向与直觉相反：把波特率从 500 kbps 提到 1 Mbps，总时间只从 ~4.3 s 降到 ~3.8 s（**收益很小**）；而"边收边写"（传输与编程重叠）、"擦除与传输流水"是**秒级**收益。这个判断是区分"跑通过"与"想清楚过"的分界线。

### 4.6 掉电安全（防变砖）

| 风险 | 对策 |
| --- | --- |
| 擦除旧 App 后掉电 → 无程序可跑 | **A/B 双区**：新固件只写非活动区，活动区始终完整 |
| 新固件写到一半掉电 | 整包校验未通过 → 不切换启动区 → 继续用旧固件 |
| 有效标志本身写坏 | 标志页存**双份 + CRC**；两份都坏判为"无有效区" |
| 两个区都失效 | 停在 Bootloader，**通过 CAN 周期发送求救帧**（携带芯片 ID 与状态），等待主站重新下发 |
| 版本回退攻击 | 记录版本号，拒绝刷入更低版本（除非显式强制） |

### 4.7 链路② + 全局：网关式 FOTA

```
云端/上位机
    │ ① HTTPS/MQTT 下发固件
    ▼
ESP32-S3 核心机
    ├─ 写入 W25Q64 → "固件仓库"（可存多版本/多节点型号）
    ├─ 自我升级（A/B + 回滚）
    └─ ② CAN 分发 → 节点一 / 节点二 IAP
```

**建议实现的命令**（EC11 + OLED 菜单或串口 CLI）：
```
ota status            # 全网版本矩阵：各节点当前版本 + 是否为最新
ota download <url>    # 下载到 W25Q64 仓库并校验
ota push node1        # 分发到节点一（带进度与耗时）
ota push all          # 顺序升级全部节点（失败隔离 + 重试）
ota rollback node2    # 强制回滚到上一版本
```

| 要点 | 做法 |
| --- | --- |
| 版本矩阵 | 各节点在遥测帧携带固件版本；主站维护节点表，OLED 显示版本一致性 |
| 失败隔离 | 单节点升级失败不阻塞其他节点；失败节点保留旧固件继续工作并上报故障码 |
| 断点续传 | 记录已成功写入的块号，中断后从断点继续 |
| 并发 | CAN 是共享总线，**升级必须顺序进行**；可在升级时临时调低其他节点遥测周期腾出带宽 |
| 仓库元数据 | 每个镜像记录 目标芯片 / 版本 / 大小 / SHA-256 / 适用节点，避免刷错固件 |

## 五、CAN 安全威胁建模

**为什么值得做**：CAN 注入攻击是汽车信息安全经典话题，而面试官很容易顺着 OTA 问"你怎么防止别人给节点刷恶意固件"。

### 问题的本质

CAN 从设计之初**没有考虑安全**：无发送者身份认证（**任意节点可伪造任意 ID**）、无加密、广播介质（无需接入点即可监听）、CAN 自身 CRC 只防传输错误**不防恶意篡改**、无重放保护。

**经典案例**：2015 年 Miller & Valasek 通过娱乐系统远程入侵 Jeep Cherokee，最终可经 CAN 控制刹车与转向，导致 140 万辆召回——汽车网络安全领域的标志性事件。

### 攻击面与本项目对策

| 攻击面 | 本项目对应 | 缓解 |
| --- | --- | --- |
| 物理接入总线 | 任意人插上 USB-CAN 分析仪 | 物理防护；网关做 **ID 白名单过滤** + 数据范围校验 |
| 伪造节点 | 一台 PC 冒充"节点一"上报假温度 | 报文 MAC / 滚动计数防重放 |
| 伪造命令 | 直接发命令帧让电机全速 | 命令需认证或进入受保护模式 |
| **恶意固件** | 通过 CAN 刷入恶意程序 | **升级需物理按键确认** + bootloader **校验签名**后才写有效标志 |
| 固件窃取 | 读走 flash 中的算法 | Flash 加密 / 读出保护 |
| 版本降级 | 刷回有漏洞的旧版本 | 版本号单调递增 + 拒绝降级 |

> **面试叙事**：把"OTA 签名校验"讲成"我意识到 CAN 无认证，所以不能只保护传输通道，还必须保护固件本身的可信性"——这是从功能思维到威胁思维的跃迁。

### 6.3 采购防坑清单

| # | 陷阱 | 对策 |
| --- | --- | --- |
| 1 | **PSRAM 模式决定 GPIO33~37 是否可用**：N16R8/N8R8 为 **Octal PSRAM → 占用 GPIO33~37**；**N8R2 为 Quad PSRAM（与 Flash 共用内部 SPI）→ GPIO33~37 空闲**。本项目无大词汇量语音模型，2 MB PSRAM 够用 |**若还未下单，选 N8R2 可让引脚规划宽松很多**（设计规格 §4.1 的避让本可避免）。下单前务必以模组数据手册确认 PSRAM 模式 |

| 5 | **TJA1050 模块的 RXD 输出是 5 V** | 本项目已确定**保留 TJA1050 ×3**：RXD 先串 1kΩ 限流（约 1.1 mA，不达标补 2kΩ 对地成分压）+ TXD 直连逐片实测（设计规格 §9.1）；后续补料优先 SN65HVD230/TCAN332 3.3V 模块 |
| 6 | **面包板 + 杜邦线接触电阻大**，CAN 差分层对反射极敏感——是"通信时好时坏"的头号原因 | CAN 的 H/L/GND **必须焊接或压接**；两端终端必接；原型阶段先用 **125 kbps** |
| 7 | 热敏/光敏模块 AO 输出范围随供电变化，DO 阈值由板上电位器决定、个体差异大 | 统一 3.3 V 供电并**实测 AO 范围**；DO 阈值逐个标定 |
| 8 | SG90 假货多，扭矩与堵转电流与标称不符 | 多买 1~2 个备用；实测堵转电流写入文档 |
| 9 | 廉价 USB-CAN 分析仪可能用 5 V 收发器 | 优先选明确用 3.3 V 收发器的版本；确认自带终端电阻开关 |
| 10 | 便宜的"5V/2A"适配器虚标，带舵机浪涌即跌压 | 用可调电源 + 示波器实测带载纹波；预留 2 倍余量。**动力轨建议 5V/5A** |

### 7.1 分阶段路线

| 阶段 | 周期 | 交付物 | 验收标准 |
| --- | --- | --- | --- |
| 1. 单节点打通 | 1 周 | 节点一固件（温度 + 电机 + 蜂鸣 + 调试口） | ADC 与数字传感器对比误差 < 1 ℃；PWM 波形示波器可测 |

| T-18 | **升级中不丢帧** | 擦除 flash 期间持续发遥测 | **无丢帧**（验证 ISR 驻 RAM 方案） | 分析仪 |
| T-19 | 节点热插拔 | 运行中接入新节点 | 主站自动识别并纳入节点表 | OLED / 日志 |
| T-20 | 版本矩阵 | 混合新旧版本节点 | 主站正确显示各节点版本与不一致状态 | OLED |
| T-21 | 协议解码健壮性 | PC 侧对解码器做模糊测试 | 无越界、无死循环、无未定义行为 | fuzzer 报告 |
| T-22 | 协议单元测试 | `ctest` 全部用例 | 100% 通过，覆盖率达标 | CI |

> **T-18 最能出彩**：它直接验证"擦 flash 会丢 CAN 帧"这个绝大多数人不知道的坑，并证明你的对策有效。**机理先行验证已前移到阶段 2**（裸片循环擦页 + 对端持续发帧数丢帧率），此处为整个 OTA 链路完成后的正式验收。
